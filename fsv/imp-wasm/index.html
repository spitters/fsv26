Imp in WebAssembly

The ImpCEvalFun chapter defines ceval_step, a step-indexed evaluation function for Imp, and proves it agrees with the evaluation relation ceval of Imp (ceval_and_ceval_step_coincide). The chapter Extraction then extracts that function to OCaml and runs Imp programs with it.

This page does the same thing in your browser. Each program below was compiled to a WebAssembly module by Peregrine, through CertiRocq's verified extraction pipeline, and the module computes ceval_step applied to that program. The button fetches the module, runs it, and reads the resulting nat out of the module's linear memory. No Rocq runs here: this is compiled code, about 40 KB per program.

The same programs over machine integers

The table above runs the chapter's definitions, in which a number is a chain of S constructors. The modules below run ImpInt.v: the same Imp, written out with nat replaced by Uint63.int, so that +, - and * are single machine instructions. Nothing is proved about this version. ceval_and_ceval_step_coincide is a theorem about the nat evaluator and does not transfer, because int wraps at 263 where nat does not. It is here for the contrast: this is what the arithmetic costs.

What the numbers are doing

The modules inherit Rocq's unary nat, so the result is a chain of S cells in linear memory and the page decodes it by walking that chain. Arithmetic is unary too: Y * Z is repeated addition, and Nat.add recurses as deep as its first argument. A browser gives WebAssembly a fixed stack of about a megabyte and no way to ask for more, so the factorial demo stops being runnable here somewhere past X = 7: X = 8 needs a 40320-deep recursion and overflows, although the same module computes it under a host that allows a large stack. subtract_slowly keeps every number small, and its 1000 iterations cost nothing, because the loop is a tail call.

This is the reason the Extraction chapter spends a section on remapping nat to a machine integer type before extracting. The second table is that trade made explicit: its results are single 64-bit words, which is why 20! runs in under a millisecond and why the proof does not come along.

The modules need the WebAssembly tail-call instructions, which current desktop Chrome and Firefox have. The drivers that produced them are ImpWasm.v (chapter definitions) and ImpIntWasm.v with ImpInt.v (machine integers); each pins a program and its input, and peregrine wasm compiles the result. One module is one closed computation, so trying your own Imp program means extracting the chapter's parser as well, which this page does not do.
